LLM API は、API の後ろにある他人の GPU、つまりホスト型のモデルです。

## どこに置くか

- 最初の AI の機能を出荷するときに置きます。運用の手間はかからず、トラフィックが少ない間はコストもかかりません。[ホスト型モデル](/research/hosted-models)でアンロックします。
- トークンの請求が大きくなったら、安定した負荷には省きます。切り替える前に、請求と忙しい GPUノードの支出を比べます。LLM API は、ほとんど遊んでいる GPUノードより安いままです。
- [トラフィックスパイク](/incidents/spike)が上限を押し超えそうなときは、ピークの前にサイズを上げます。

## 仕組み

処理するトークンごとに課金され、マネージドコンポーネントなので置くのにコストはかからず、すべてのリージョンにサービスを提供します。推論の呼び出しはアプリサーバーから届き、その下流にコンポーネントはありません。各プロンプトは最初のトークンまで決まった時間を待ち、[GPUノード](/components/gpu)より長く待ちます。[モデル推論](/glossary/model-inference)を参照してください。

レート制限があります。サイズを 1 段上げるごとに利用枠が上がり、毎秒受け付けるプロンプト数が 2 倍になり、上限を超えるとプロンプトはすぐに `throttled` で失敗します。[レート制限](/glossary/rate-limiting)を参照してください。

## どう壊れるか

- 枠を超えると、プロンプトは `throttled` で失敗します。
- コストはプロンプトごとに増えます。台帳でサードパーティのコストを見ます。
- どのプロンプトも最初のトークンを待つので、AI プロンプトの p99 は高いままです。

守りにもなります。[GPU不足](/incidents/gpu-shortage)の間も、GPUノードと LLM API の両方にリンクしたアプリサーバーはプロンプトを処理し続けます。

### [インスタンス障害](/incidents/instance)

- **兆候:** LLM API のカードが灰色になり、吹き出しに「この VM の下のホストが死にました。請求は続きます。」と出ます。そこへ送ったリクエストは行き場所を失います。
- **今すぐ:** ノードを選んで**置き換え**をクリックします。資金がかかり、コールドで戻ります。
- **防ぐ:** 2 つ目の LLM API のノードを動かし、プロンプトに別の行き先を作ります。

## ヒント

- GPUノードを置いたあとも、予備として LLM API をリンクしたままにします。
