リードレプリカは PostgreSQL や MySQL のストリーミングレプリカを指します。読み取りに答えるプライマリのコピーです。

## どこに置くか

- 再起動なしではデータベースが足せない読み取り容量を足すために置きます。サイズ変更はデータベースを再起動し、コールドで戻ります。レプリカは設計に加わり、プライマリが働き続ける間に読み取りの取り分を引き受けます。
- レポートをプライマリから移すために置きます。レポートはスキャンで、キャッシュできず、データベースのバッファキャッシュを追い出します。レプリカをリンクするとスキャンはレプリカへ行き、プライマリのほかのクエリはキャッシュを保ちます。
- 読み取りでデータベースの CPU が高く、[キャッシュ](/components/cache)がホットなデータを保持できないときに置きます。キャッシュはホットな行の繰り返される読み取りに答え、レプリカはどんな読み取りにも答えるので、キャッシュが外したロングテールを引き受けます。プライマリとレプリカを L4 の[ロードバランサー](/components/lb)にリンクすると（[L4 ロードバランシング](/research/l4-lb)のリサーチが必要です）、読み取りがそのアルゴリズムで分散します。書き込みはプライマリにだけ行きます。手前に[コネクションプーラー](/components/pooler)がある場合は、プーラーをロードバランサーにリンクします。プーラーは外へのリンクを 1 本しか取らないからです。
- 組み合わせが書き込み中心なら省きます。必要なのはより大きなプライマリで、レプリカを増やすことではありません。
- すべての読み取りが新しくなければならず、[read-your-writes ルーティング](/research/ryw-routing)がないときは省きます。レプリカは必ず遅れ、一部の読み取りが `stale` で失敗します。

| 必要                                       | 使うもの                                                              |
| ------------------------------------------ | --------------------------------------------------------------------- |
| 書き込みを増やす                           | より大きな[データベース](/components/database)、またはシャード        |
| ホットな行に当たる読み取りを減らす         | [キャッシュ](/components/cache)。ホットなデータが収まる間の最も安い手 |
| どの行でも読み取りを増やす、またはレポート | リードレプリカ                                                        |

[古いチェックアウト](/sandboxes/stale-checkout)と[失われた書き込み](/sandboxes/missed-write)のサンドボックスが古い読み取りを示します。

::Sandbox{id="stale-checkout"}

## 仕組み

データベースをレプリカにリンクします。そのリンクが書き込みログを送り、レプリカが何かをコピーする唯一の方法です。クエリは運びません。データベースがリンクされていないレプリカは読み取りを引き受けず、カードに「なし: データベースをリンクしてください」と出ます。レプリカは 1 つのデータベースをコピーするので、そのデータベースのエンジンに従います。読み取りを送るために、アプリサーバーか L4 のロードバランサーがレプリカにリンクします。

[データベース](/components/database)と同じ容量モデルを使い、インスタンスの種類とサイズがあり、独自の接続上限を持ちます。届くのは読み取りクエリとレポートのスキャンだけで、下流にコンポーネントはありません。プライマリのエンジンで動くので、接続上限もプライマリに従います。書き込みはやはりプライマリへ行きます。リンクしたデータベースがデータグループも決めます。レプリカはどこに描かれてもそのデータベースのグループに属するので、グループの行と容量はそれに対して数えられます。

レプリカはデータベースより安く済みます。置くのも安く、同じサイズのデータベースより箱の請求が 30% 安いです。バックアップも、プロビジョンド IOPS の段も、サイズを合わせる書き込み経路もないからです。

レプリカはプライマリより遅れ、ラグは書き込みのレートとともに増えます。20 ms に、毎秒の書き込み 1 回ごとに 2 ms を足したものです。その窓の中の読み取りの 4 分の 1 は、書き込みが変えたばかりの行を求めるので、その割合の読み取りが古い値で返り、最大 15% になります。カードがラグを示します。古い答えは API の読み取りと、自分の書き込みを読むチェックアウトを失敗させますが、ページビューは受け入れます。[レプリケーションラグ](/glossary/replication-lag)を参照してください。

プライマリが消えたら 1 つを昇格します。レプリカがプライマリになり、元のプライマリがそのレプリカになり、書き込みが分かれないように遮断されます。同期レプリカは飛行中の書き込みがないので何も失いません。非同期のものはプライマリが送っていなかった書き込みを保持しているので、昇格するとそれを失います。新しいプライマリはコールドで始まります。[フェイルオーバー](/design/07-data-tier#failover)を参照してください。

## オプション

::Options{id="replica"}

- **レプリケーション**: 同期は、プライマリのすべての書き込みにこのレプリカを待たせます。そのため古い読み取りは返さず、落ちている間はすべての書き込みがタイムアウトします。非同期が既定で遅れることがあり、それを[read-your-writes ルーティング](/patterns/read-your-writes)が補います。[レプリケーション戦略](/patterns/replication-strategies)を参照してください。
- **エンジン**: レプリカはプライマリのエンジンで動くので、ここで選ぶものはありません。接続上限、クエリのコスト、ラグはすべてプライマリに従います。
- **昇格**: レプリカがプライマリになり、元のプライマリがそのレプリカになります。同期レプリカは何も失わず、非同期のものは飛行中の書き込みを失います。

## どう壊れるか

- ほかのすべてのデータベースと同じく、上限を超えた接続を拒みます。

### [レプリケーションラグ](/incidents/repl-lag)

- **兆候:** 書き込みのバーストでレプリカが数秒遅れ、書き込みの後の読み取りが `stale` エラーで返ります。
- **今すぐ:** 読み取りを処理するアプリサーバーで、選択を**自分の書き込みを読む**にして、その読み取りをプライマリへ送ります。[read-your-writes ルーティング](/research/ryw-routing)が必要です。
- **防ぐ:** [read-your-writes ルーティング](/research/ryw-routing)をリサーチし、チェックアウトを処理するアプリサーバーで**自分の書き込みを読む**をオンにします。**同期**のレプリカも、[同期レプリケーション](/research/sync-replication)で追いつきます。

### [インスタンス障害](/incidents/instance)

- **兆候:** レプリカのカードが灰色になり、インスペクタに「この VM の下のホストが死にました。請求は続きます。」と出て、その取り分の読み取りが失敗します。
- **今すぐ:** インスペクタの**置き換え**を押し、値段を払います。コールドで戻ります。
- **防ぐ:** 2 つ目のコピーを動かします。[ロードバランシング](/research/load-balancing)がコピーをロードバランサーの後ろに置き、[ヘルスチェック](/research/health-checks)が死んだホストを飛ばします。

### [ゾーン障害](/incidents/zone)

- **兆候:** 1 つのゾーンのすべてのノードが一斉に灰色になります。
- **今すぐ:** ゾーンを早く戻す方法はありません。**フェイルオーバー**は**スタンバイ**を昇格しますが、このコンポーネントはスタンバイを持たないので、最大 120 秒で自然に終わります。
- **防ぐ:** [マルチゾーン](/research/multi-az)をリサーチし、ゾーン設定でコピーを別のゾーンに置きます。

### [リージョン障害](/incidents/region)

- **兆候:** 1 つのリージョンのすべてのノードが一斉に灰色になり、そのリージョンのボードも一緒に灰色になります。
- **今すぐ:** 速くする方法はありません。**フェイルオーバー**はデータを持たないノードだけを移すので、これが落ちたままインシデントの終わりまで続きます。カタログでは 180 シミュレーション秒、エラーバジェットが効いてからは 60 秒です。リージョンにまたがるストアなら何もする必要はありません。
- **防ぐ:** [マルチリージョン](/research/multi-region)と [GeoDNS](/research/geo-dns)をリサーチし、2 つ目のリージョンでコピーを動かします。

## ヒント

- チェックアウトを処理するアプリサーバーで read-your-writes をオンにします。
- アプリサーバーからレプリカをリンクすると、レポートはすぐにプライマリから離れます。
- 書き込み中心の組み合わせには、レプリカを増やさずより大きなプライマリを買います。

:::Note{tone="real"}
実際の Postgres では非同期レプリケーションが既定なので、実際のレプリカも遅れます。[read-your-writes の一貫性](/glossary/read-your-writes-consistency)を参照してください。
:::
