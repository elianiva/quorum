遅い答えは速い答えより少なく払い、とても遅い答えは何も払いません。リクエストは、ユーザーが十分速く答えを受け取ったときにだけ、その価値の全額を稼ぎます。Quorum は「十分速い」を業界の指標である Apdex で測り、同じ指標でユーザーが留まるかどうかも決めます。

## 満足、許容、いらだち

どのリクエスト種別にも目標時間 T があります。ページビューの T は API 読み取りより長いです。ページには少し時間がかかると人が期待するからです。処理された各リクエストはどれかの区分に入ります。

| 区分     | 条件                          | 稼ぐもの   |
| -------- | ----------------------------- | ---------- |
| 満足     | レイテンシが T まで           | 価値の全額 |
| 許容     | レイテンシが T を超え 4T まで | 価値の半分 |
| いらだち | レイテンシが 4T を超える      | なし       |
| 失敗     | あらゆるエラー                | なし       |

[Apdex](/glossary/apdex) は満足したリクエストの割合に、許容の割合の半分を足したものです。

```latex
\text{Apdex} = \frac{\text{satisfied} + \text{tolerating} / 2}{\text{total}}
```

Apdex が 1 なら、すべてのユーザーが満足しました。Apdex が 0.5 は、すべてのユーザーが待ちを許容したという意味にも、半分が満足して半分が諦めたという意味にもなります。

::Quiz{question="ある API 読み取りの目標 T は 200 ms です。1件の読み取りが 500 ms で答えます。それは何を稼ぎますか？" options="価値の全額|価値の半分|なし" answer="2" explain="500 ms は T を超えていますが 4T（800 ms）未満なので、そのリクエストは許容で、半分を稼ぎます。"}

## 平均レイテンシではなく Apdex を使う理由

平均レイテンシは全員を1つの数値に混ぜ、Apdex は人を数えます。5秒待ったユーザーは、ほかがどれだけ速くても失われるので、Apdex はそのリクエストに0を与えます。少し長く待ちすぎたユーザーは失われないので、Apdex は半分の点を与えます。

Apdex は Quorum のレイテンシの計算方法にも合います。応答時間は曲線に沿って広がるので、どの種別でも一定の割合が常に目標より遅くなります。種別ごとに、シミュレーションは答えたリクエストのうち T 未満と 4T 未満の正確な割合を計算します。その割合はノードが埋まるにつれて滑らかに下がり、平均が悪く見えるずっと前から下がります。[レイテンシとパーセンタイル](/explanation/latency)を参照してください。

ボットは Apdex に数えません。アップロードやエクスポートのようにキューを通る種別は、キューに入れた時点ではなく結果が出た時点で採点されます。

## リクエストの価値

売上は、すべての種別について、その価値に Apdex の点を掛けたものの合計です。

```latex
\text{revenue} = \sum_{\text{kinds}} \text{rate} \times \text{value} \times \left(\text{satisfied} + \text{tolerating} / 2\right)
```

価値は種別によって大きく違います。チェックアウトはページビューよりはるかに価値があり、ボットは何の価値もないので、同じレイテンシの問題でもお金の経路では高くつきます。種別の価値を変えるものは3つです。

- **機能。** 種別の稼ぎを増やす機能があります。[チーム](/team#features)の一覧を参照してください。
- **スタック。** リクエストに答えるフレームワークが稼ぎを変えることがあります。
- **事業。** 事業ごとにリクエストあたりの価値を決めます。

**有料プラン**の機能は2つ目の源を加えます。有料ユーザー1人につきカレンダー1日ごとのサブスクリプションです。リクエストに依存しないので、収入を滑らかにし、ユーザーを保つことに報います。

:::Note{tone="real"}
Apdex Alliance がこの式を標準として公開し、監視の道具はいまもこれを報告します。実際の売上がちょうど T で半分になるわけではありませんが、形は合っています。2009年の Google の研究では、400 ms の余分な遅延が人々の検索量を下げ、その損失は遅延が消えたあとも続きました。
:::

## Apdex はユーザーも動かす

同じ指標が成長を決めます。時代ごとに Apdex の目標があります。直近のカレンダー1時間のユーザーの Apdex がそれを上回っている間はユーザーが増え、下回ると離れます。遅い設計はお金を2度失います。リクエストごとに1度、そしてユーザーが去ることでまた1度です。[ユーザーと成長](/explanation/users-and-growth)を参照してください。

## 決済の引き出し

売上は[決済](/components/payments)の引き出しで待ち、回収を選ぶと資金へ移ります。引き出しは現在のレートでおよそ1分ぶんの売上を保ち、大きいサイズほど多く保ちます。引き出しが満杯の間に届いた売上は失われます。

引き出しはガレージの最初の数分にやることを与え、そのあとは邪魔をしなくなります。[Stripe Billing](/research/stripe)のリサーチで自動で回収します。会社を閉じている間は時計が止まるので、引き出しが満杯になることはありません。そのあと資金がどこへ行くかは[資金、支出、資金調達](/explanation/money)にあります。

## 収入を上げる方法

毎秒の収入は変更の最良の点数なので、システムが落ち着いてから前後で比べます。利得のほとんどは3つの動きのどれかから来ます。

1. ボトルネックを取り除き、より多くのリクエストに答えられるようにします。
2. 答えたリクエストを速くし、より多くが満足するようにします。
3. 高価な種別を先に守り、遅くなってもページビューを犠牲にし、チェックアウトは犠牲にしないようにします。
