Quorum は初期のスタートアップのように、ほとんど見えない状態で始まります。見えるのは負荷のバー、リクエストのレート、平均レイテンシ、そしてエラーの数値1つです。可観測性はここで2つの仕事をします。リサーチを買う通貨であるインサイトを生み出すことと、可観測性のリサーチがシステムのどれだけを見られるかを決めることです。

## アナリティクスがトラフィックをサンプリングする

[アナリティクス](/components/analytics)のノードはタップです。どのノードでもリンクすると、そのノードのトラフィックをサンプリングします。各サンプルはリクエスト種別を持ち、その種別のプールにインサイトを加えます。失敗したリクエストやユーザーをいらだたせたリクエストは失敗のプールにも加えます。[時代とリサーチ](/explanation/progression)がインサイトが種別ごとに来る理由を説明します。

収量は平方根に従います。

```latex
\begin{aligned}
\text{Insight} \left(\text{kind}\right) &= \sum_{\text{over Component types}} \sqrt{\text{sampled requests of that kind per second}} \\
\text{Failure} &= 3 \times \sum_{\text{over Component types}} \sqrt{\text{sampled failed requests per second}}
\end{aligned}
```

平方根から2つのルールが出ます。

- **広さは大きさに勝る。** トラフィックを4倍にしてもインサイトは2倍にしかなりませんが、コンポーネントの種類ごとに独自の項が加わります。ロードバランサー、アプリサーバー、キャッシュ、データベースでサンプリングした読み取りは、1つのノードでサンプリングするより4倍多くを教えます。
- **コピーは2度数えられない。** アプリサーバー10台で項は1つなので、ノードを多くに分けても新しいことは学べません。

失敗のプールはサンプルあたり3倍稼ぎます。健全な設計はめったに失敗しないからです。失敗したかユーザーをいらだたせたリクエストは満額で数え、許容されたものは一部で数えます。わざと失敗させるのはそれでも悪い取引です。失敗はユーザー、売上、エラーバジェットを食うからです。

## 見ることは何かを犠牲にする

アナリティクスには毎秒のサンプル数でのキャパシティがあり、サイズを1段上げるごとに倍になります。それを超えたサンプルは均等に捨てられます。サンプルレートは1%、5%、10%（既定）、50%、100%から選びます。

高いレートはより多くのインサイトを与えますが、比例はしません。100% は 10% のおよそ3倍のインサイトを与え、次のものを食います。

- タップしたすべてのノードの **CPU**。
- タップしたすべてのホップの**レイテンシ**。Apdex を下げることがあります。
- アナリティクスの請求の**ストレージの支出**。

アナリティクスはトレースを保持期間のあいだも保ちます。15分、1時間、6時間のシミュレーション時間です。長い期間はストレージを多く食い、各インサイトのプールがより多くを持てます。プールは現在のレートでおよそ1期間ぶんのインサイトを持つので、巨大な残高をためて時代が開いたときにまとめて買うことはできません。

:::Note{tone="real"}
可観測性の請求は実際のチームも驚かせます。実際のトレーシングのシステムはサンプリングでその費用を抑えます。リクエストの一部を保ち、まれな事象を取りこぼすかもしれないことを受け入れます。
:::

## 可視性のはしご

シミュレーションは台帳のすべての数値を常に計算し、リサーチが変えるのはインターフェースが示すものだけです。[パーセンタイル](/research/percentiles)のないプレイヤーも遅いリクエストに売上を食われますが、p99 は見えません。

[可観測性のトラック](/research)の各段階がより多くを見せます。

| リサーチ                                       | 見えるもの                                                                       |
| ---------------------------------------------- | -------------------------------------------------------------------------------- |
| [構造化ログ](/research/logs)                   | 原因ごとに分かれたエラー。`stranded`、`dropped`、`refused`、`down`、`oom` など。 |
| [メトリクス](/research/metrics)                | すべてのノードの履歴のグラフと、ダッシュボード。                                 |
| [パーセンタイル](/research/percentiles)        | 平均の隣の p50、p95、p99。                                                       |
| [アラート](/research/alerting)                 | エラー、p99、飽和がしきい値を越えたときのページャー。                            |
| [SLO ダッシュボード](/research/slo-dashboards) | HUD のエラーバジェットと、ダッシュボードのその消費率。                           |

[分散トレーシング](/research/tracing)はそのトラックにあり、ほかの項目がそれを要求します。ダッシュボードにサービスとリソースの行を加えます。各リクエスト種別のレート、エラー、時間、そして各ノードの使用率、飽和、上限です。

::Track{track="observability"}

## 常にオンの2つの道具

**ボトルネックの印**は、キャパシティを足すと最も売上が増えるノードを名指しします。ほかが見えるようになる前に、ゲームを遊べる状態に保ちます。

**離脱の内訳**はユーザーの数値から開き、各リージョンの Apdex を奪う行をリクエスト種別と原因ごとに並べます。リサーチが詳細を加えます。構造化ログがあれば失敗が原因を名指しし、パーセンタイルがあれば遅い行が p99 を示します。[ユーザーと成長](/explanation/users-and-growth)がその読み方を説明します。

## アラートとアラート疲れ

アラートがあると、5つの既定のルールがシステムを見張ります。

- エラー率が30秒間 1% を超えたままです。
- ある種別の p99 が30秒間、その Apdex 目標の4倍を超えたままです。
- あるノードが60秒間、使用率90%を超えたままです。
- あるキューの最も古いタスクが60秒間、30秒より古いままです。
- エラーバジェットがシリーズ A から、30秒間、均等な消費率の10倍を超えて消費されます。

各ルールは感度を上げ下げできます。背後にインシデントのないアラートは誤報で、カレンダー1日に5回の誤報があると、そのルールは無視として印を付けられ、ページャーを鳴らすのをやめます。これがアラート疲れで、実際のチームにもあります。理由なく呼ばれる人は見るのをやめます。うるさいルールはそれと暮らすのではなく調整します。

## ダッシュボード

ボードはいまのシステムを示し、ダッシュボードは時間の上で示します。メトリクスのあと `D` で開きます。最初の行が[4つの黄金のシグナル](/glossary/four-golden-signals)を描きます。トラフィック、レイテンシ、エラー、飽和です。グラフの線が直近の設計の変更とインシデントの始まりを示すので、線が直したあとに動いたか、その前に動いたかを確かめられます。[注釈](/glossary/annotation)を参照してください。

長い期間は平均した時間のブロックを示しますが、p99 の線は各ブロックで最も悪い分を描きます。平均では急増が隠れるからです。[ダウンサンプリング](/glossary/downsampling)と[p99 を読む](/guides/read-p99)を参照してください。
