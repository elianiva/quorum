ノードは満杯になるずっと前に遅くなります。どのノードにもキャパシティ、つまり毎秒できる仕事の最大量があり、どれだけ埋まっているかがリクエストの待ち時間を決めます。その関係は曲線で、Quorum で出会う遅さのほとんどを説明します。

## 使用率

ρ（ロー）と書く[使用率](/glossary/utilization)は、届く仕事をノードのできる仕事で割ったものです。

```latex
\text{utilization} = \frac{\text{offered work}}{\text{capacity}}
```

仕事はノード自身の単位で測ります。アプリサーバーは CPU 時間、ワーカーのスロット、メモリ、ネットワークを数えます。データベースは CPU と接続を数えます。最も厳しい上限がノードのキャパシティを決めます。各カードの負荷のバーが使用率を示し、上がるにつれてカードの色が変わります。

- **70% 未満。** 健全です。リクエストはほとんど待ちません。
- **70% から 90%。** 琥珀色です。待ち時間が速く伸びます。
- **90% 以上。** 赤です。テールは中央値の数倍です。
- **100% 超。** 飽和です。ノードはできるだけ処理し、残りをエラーとして落とします。

## ホッケースティック

待ち時間は `ρ / (1 − ρ)` にサービス時間を掛けたものに比例して伸びます。使用率50%では、リクエストは処理にかかるのとほぼ同じだけ待ちます。90%では、およそ9倍待ちます。曲線は長く平らなままで、そのあとホッケーのスティックのように跳ね上がります。

つまり使用率85%のノードは「15% の余裕があって問題ない」わけではありません。すでに遅く、トラフィックが少し上がるだけでずっと遅くなります。同じ曲線は、熱いノードへの小さなアップグレードが大きく効くことも意味します。

::Quiz{question="あるノードが使用率90%で動いています。キャパシティを2倍にして45%になりました。キューの待ちはおよそどれだけ変わりますか？" options="半分になる|およそ10分の1になる|変わらない" answer="2" explain="待ちは ρ / (1 − ρ) で伸びます。90% では9、45% ではおよそ0.8なので、待ちは10倍以上減ります。"}

:::Note{tone="real"}
実際のサーバーは単一サーバーの待ち行列（M/M/1）に正確には従いません。多くはワーカーが多数あり、サービス時間も不揃いだからです。それでも形は保たれます。レイテンシは低い負荷では平らなままで、使用率が100%に近づくと急に上がります。運用者が余裕を残すのはまさにこの理由です。
:::

## 余裕は無駄ではない

需要は日々の周期に従い、夕方のピークは日々の平均よりずっと高いので、平均に合わせた設計は毎晩赤くなります。余ったキャパシティはトラフィックの急増とノード1つの喪失も吸収します。健全な設計は、たいていの時間、琥珀色の線よりずっと下で動きます。

余裕は3つの方法で買えます。

- **スケールアップ。** ノードを大きいインスタンスにリサイズします。1段ごとに vCPU と RAM が倍になりますが、ノードは再起動しコールドで戻ります。余分なコアを使えないソフトウェアもあります。
- **スケールアウト。** DNS かロードバランサーの後ろにコピーを加えます。コンポーネントのコピーは、1つ前より配置が高くつきます。
- **需要に合わせてスケール。** [オートスケーラー](/components/autoscaler)は負荷が目標を越えるとコピーを加え、負荷が下がると取り除きます。新しいコピーは起動に時間がかかるので、どのみち余裕を残します。

インスタンスのサイズと価格は[垂直と水平のスケーリング](/glossary/vertical-and-horizontal-scaling)と[インフラ](/infrastructure)の一覧を参照してください。

## CPU だけでなくスロットも

アプリサーバーは CPU が遊んでいても満杯になります。PHP-FPM、Gunicorn、Puma、Tomcat のようなランタイムは、リクエストが終わるまでワーカーかスレッドを1つずつ握ります。データベースを待つ時間も含みます。すべてのスロットが待つと、CPU にすることがないのに新しいリクエストがキューに入ります。

[リトルの法則](/glossary/littles-law)がそれを説明します。使用中のスロットは、到着のレートに各リクエストがスロットを握る時間を掛けたものです。待ちが倍になれば、決まったプールが処理できるのは半分のリクエストです。遅い呼び出しを直すか、ワーカーを増やすか、スロットを握らずに待つランタイムへ移ります。[ランタイム](/runtimes)のページが各ランタイムのモデルを示し、[リクエストの流れ方](/explanation/requests)がこれがアプリサーバーとデータベースを結ぶ理由を説明します。

## キュー: わざと待つ

[キュー](/components/queue)は、[ワーカー](/components/worker)があとで処理できるように仕事を蓄えるコンポーネントです。キューにリンクしたアプリサーバーは、アップロードのリサイズやエクスポートの作成のような、一部のリクエストの遅く非同期的な部分を渡します。ユーザーはキューに入れるまでしか待ちません。

キューはワーカーが追いつかなくなっても仕事を落としません。あふれた分を**深さ**として蓄え、ワーカーが処理できるときに流し出すので、バーストはエラーではなく遅延になります。深さには代価があります。

- 新しいタスクは、キューにすでにあるすべてのタスクの後ろで待ちます。ユーザーはアップロードやエクスポートを結果が出た時点で採点するので、深いキューはいらだたせます。
- 長さの上限がなければ、ワーカーがタスクの到着より遅く流すと、深さは際限なく伸びます。
- キューの最大長は[バックプレッシャー](/glossary/backpressure)です。それを超えるとキューは新しいタスクを断り、タスクを送ったリクエストはすぐ失敗します。

失敗したタスクはあとでもう一度試すために戻り、デッドレターキューがなければ、必ず失敗するタスクは戻り続けます。[デッドレターキュー](/glossary/dead-letter-queue)と[ポイズンメッセージ](/incidents/poison)のインシデントを参照してください。

## 赤いカードを読む

カードが赤くなったら、最も厳しい上限は何かを問います。CPU ならキャパシティを足すか仕事を安くします。スロットなら下流の遅い呼び出しを探します。接続なら[エラーとリトライ](/explanation/errors-and-retries)を読みます。ボトルネックの印が、どの赤いカードを先に直すかを教えます。
