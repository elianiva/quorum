状態がスケーリングの難しい部分です。アプリサーバーはデータを持たないのでコピーが簡単で、10個のコピーは1個と同じくらい正しいです。データは違い、どのコピーもほかと合意しなければユーザーは間違った答えを見ます。どの会社でもデータ層が長期的な難題になるのはそのためです。

## データベースが真実の源

[データベース](/components/database)は読み取りのクエリ、書き込みのクエリ、トランザクションに答えます。よりよいコンポーネントをリンクするまでは、ほかの3つの仕事も下手にこなします。全文検索、行として保存するアップロードのファイル、レポートのスキャンです。どれも普通の読み取りよりずっと多くの CPU を食います。[検索エンジン](/components/search)、[オブジェクトストレージ](/components/storage)、[データウェアハウス](/components/warehouse)がその仕事を引き取ります。

データベースには4つの上限があります。

- **CPU。** どのクエリも CPU を食い、再起動したばかりのコールドなデータベースはクエリあたりより多くを必要とします。
- **接続。** Postgres は接続ごとにプロセスを1つ動かし、決まった数だけ受け入れます。MySQL は各接続にスレッドを与え、数倍多く持ちます。アプリサーバーを増やすとこれが悪化する理由は[エラーとリトライ](/explanation/errors-and-retries)を読んでください。
- **ボリュームの IOPS。** どの書き込みも、バッファキャッシュに外れたどの読み取りもディスクを待ちます。汎用のボリュームは毎秒 3,000 に答え、プロビジョンドのものは 64,000 に答えます。
- **バッファキャッシュ。** レポートのスキャンがメモリを冷たいデータで満たします。ほかの読み取りはディスクへ行き、書き込みはスキャンの後ろで待ちます。分析とトランザクションがデータベースを共有すべきでないのはこのためです。[OLTP と OLAP](/glossary/oltp-and-olap)を参照してください。

大きな箱は最初の2つの上限を上げます。シャーディングは書き込みの CPU の上限を上げます。各シャードが書き込みの取り分を取るからですが、各シャードは独自のデータベースのように請求されます。

## 2つのエンジン、2つの仕事の形

Postgres と MySQL は同じ仕事を違う費用で行います。Postgres は約 8 MB ずつで100の接続を持ち、読み取り、スキャン、全文検索に MySQL よりおよそ 5–10% 安く答えます。MySQL は約 1 MB ずつで500の接続を持ち、書き込みとチェックアウトにおよそ30%安く答えます。InnoDB が行をその場で更新するからです。スキーマもオンラインで変えますが、Postgres の多くの `ALTER` はテーブルのロックを取り、VACUUM のために死んだ行を保つのは Postgres だけなので、テーブルの肥大に遭うのも Postgres だけです。読み取りの多い会社は Postgres を、書き込みの多い会社は MySQL を望みます。

レプリカは常にプライマリのエンジンで動き、エンジンの変更はすべてのデータベースに一度に着地します。レプリケーションは一致するエンジンの間でしかコピーしません。

## 複数のデータベース: まとめる

2つ目のデータベースは従属ではありません。1つのデータセットを持つデータベースをまとめて箱で囲みます。箱が1つの**データグループ**を作り、そのトポロジがそれらのデータベースがグループの行をどう共有するかを決めます。単一プライマリ（開始時）は1つのデータベースで書き込みを受け、リードレプリカで読み取りを受けます。シャードは各データベースにグループの行の区画を与えるので、書き込みはスケールしますが、シャードをまたぐトランザクションは最大3×かかり、どちらのシャードでも失敗し得ます。マルチリーダーはすべての行をすべてのデータベースへコピーし、それぞれが書き込みを受けられるので、ローカルの書き込みは速いですが、認証が競合する書き込みを落とし（先のコミットが勝ち）、どの書き込みも複製に 1.25× の CPU がかかります。グループのトポロジを切り替えるとその行が動きます。再シャーディングと同じく 24 開発時間と 1 GB あたり1分です。データベースが1つのグループには動かす先がないので、選択をすぐに受け取り、箱に2つ目のデータベースが入ったときにコピーが始まります。

行はサービスに従います。各サービスは会社のデータの等しい取り分を持ち、グループはデータストアがその中にあるサービスの取り分を持ちます。2つのグループが互いの行に触れることはなく、どちらも相手のために共有データベースの罰を受けません。1つのボードが2つの独立した製品を持てるのはそのためです。箱の外のデータベースは自分の取り分を持ち、単独で立ちます。

クォーラムのストア（[ワイドカラムストア](/components/wide)）と合意（[分散 SQL](/components/dsql)）は「複数のノードで書き込む」への別の答えです。クォーラムは読み取りで N のうち R を、書き込みで N のうち W を待ち、合意はどの書き込みでも多数派を待ちます。[トポロジ](/design/07-data-tier#topologies)を参照してください。

## 遅いクエリは育つまで隠れる

2つのコードの問題は最初は少ししかかからず、後で多くかかります。

**インデックスのないクエリ**はテーブルをスキャンします。費用は行の数とともに増え、行はユーザーとともに増えるので、ガレージでは見えず、後でボトルネックになります。[スロークエリ](/incidents/slow-query)のインシデントがこの問題です。[クエリ分析](/research/query-analysis)がそれを示し、インデックスを追加のタスクが直します。

**N+1 クエリ**は、リストの項目ごとにクエリを1つ送る ORM から来ます。Laravel、Rails、Django は、Eager loading を出荷するまでページビューと API 読み取りで余分な読み取りをします。[N+1 クエリ](/glossary/n1-query)を参照してください。

## キャッシュ: データベースの前のメモリ

[キャッシュ](/components/cache)は読み取りのクエリにメモリから答え、外れたものをデータベースへ送ります。ヒット率がどれだけ負荷を引き受けるかを決めます。

```latex
\text{hit ratio} = \sqrt{\frac{\text{memory}}{\text{hot data}}} \times \text{TTL factor} \times \text{write penalty} \times \text{warmth}
```

平方根は偏ったアクセスを模します。ほとんどの読み取りは少数の熱いキーを求めるので、小さなキャッシュでも最も熱いキーはすでに持っており、最初の 1 ギガバイトは10番目より価値があります。熱いデータはユーザーとともに増えるので、前の時代に十分だったキャッシュが次の時代には小さすぎることがあります。

書き込みはキーを無効にするので、書き込みの多い配合はヒット率を下げます。長い TTL はヒットを増やしますが、古いデータをより多く返します。再起動したキャッシュはコールドで戻り、外れた読み取りが一斉にデータベースへ行きます。これが[キャッシュスタンピード](/glossary/cache-stampede)です。[スタンピード保護](/research/stampede-protection)と[キャッシュのウォーミング](/research/cache-warming)がそれを和らげます。

:::Note{tone="real"}
Redis は1つのメインスレッドでコマンドに答えるので、1つのコアが Redis のノードを制限し、1つの遅いコマンドがすべてのクライアントを止めます。Memcached はすべてのコアを使いますが、再起動で何も保ちません。Quorum はどちらも違う上限を持つキャッシュのエンジンとして模します。
:::

## リードレプリカ: 読み取りは増え、データは古くなる

[リードレプリカ](/components/replica)はデータベースのように動きますが、読み取りとレポートにだけ答えます。書き込みはプライマリへ行き、そのあとレプリカへ流れるので、レプリカは常に少し遅れており、ラグは書き込みのレートとともに伸びます。[レプリケーションラグ](/glossary/replication-lag)を参照してください。

3つのノードが忙しいデータベースから負荷を引き取り、それぞれに独自の仕事があります。

- より大きな[データベース](/components/database)は書き込みへの唯一の直し方です。最も費用がかかり、リサイズは再起動を伴います。
- [キャッシュ](/components/cache)は読み取りへの最も安い直し方で、同じ熱い行が何度も読まれる間は効きます。レポートには答えられず、書き込みが増えるとヒット率が下がります。
- リードレプリカはどの行の読み取りにも答え、レポートを引き受け、データベースの箱の価格の 0.7× で、置いても何も再起動しません。読み取りの一部は古いまま返ります。

遅れたレプリカからの読み取りは古いデータを返すことがあります。それが問題になるかは種別次第です。

- ページビューは少し古いデータを受け入れます。
- 古いまま返ってきた API 読み取りは `stale` として失敗します。
- 自分の書き込みを読むチェックアウトは `stale` として失敗し、実際のお金を食います。

[自分の書き込みを読むルーティング](/research/ryw-routing)は気にする読み取りをプライマリへ送ります。たいていの古いデータのエラーを直し、代価としてプライマリにいくらかの読み取りの負荷がかかります。

## クォーラム: ゲームの名前の由来

[ワイドカラムストア](/components/wide)は各キーを N 個のレプリカに保ちます。2つの数を選びます。読み取りが問い合わせるレプリカの数 R と、書き込みが待つレプリカの数 W です。

```latex
\begin{aligned}
R + W &> N && \qquad \text{every read asks at least one replica that has the latest write} \\
R + W &\leq N && \qquad \text{a read can miss the latest write: eventual consistency}
\end{aligned}
```

小さい R と W は速いです。各操作がより早い返事を待つからで、レプリカの操作も少なくて済みます。代価は、弱いクォーラムが古い読み取りを返すことです。すべてのレプリカを必要とするクォーラムは、1つのレプリカが落ちている間は失敗します。[クォーラム](/glossary/quorum)を参照してください。

::Quiz{question="あるワイドカラムストアが N = 3 のレプリカを保ちます。どの設定ならすべての読み取りが最新の書き込みを見ますか？" options="R = 1、W = 1|R = 1、W = 2|R = 2、W = 2" answer="3" explain="R + W > N になるのは R = 2 と W = 2 だけです。ほかの設定では、読み取りが最新の書き込みを取りこぼしたレプリカにだけ問い合わせることがあります。"}

重なりは単一の順序だった履歴を与えません。同時の書き込みは依然として競合するので、強いクォーラムでもチェックアウトでときどき古い読み取りや重複が出ます。[分散 SQL](/components/dsql)のノードはそれを合意で直します。どの書き込みもレプリカの多数派を待ちます。1つのリージョンの中では安く済みますが、リージョンをまたぐとどの書き込みも長い往復を払います。[Raft](/glossary/raft)を参照してください。

## ホットキー

データをノードに散らすのは、負荷も散るときにだけ効きます。[ホットキー](/incidents/hot-key)のインシデントでは、読み取りの大きな割合が1つのキーを求めます。有名人の投稿などです。そのキーは1つのシャードに住むので、そのシャードが飽和し、ほかは遊びます。[ハイブリッドなファンアウト](/research/hybrid-fanout)がホットキーをシャードへ散らせます。[ホットキー](/glossary/hot-key)を参照してください。

## すべての裏にある型

Quorum のどのデータの選択も、速さ、新しさ、生存の間で引き換えます。キャッシュとレプリカは新しさで速さを買い、強いクォーラムと合意は速さで新しさを買います。ほかのゾーンやリージョンのコピーは支出で生存を買います。データのトラックが各道具の裏のリサーチを示します。

実践の手順は[データベースをスケールする](/guides/scale-the-database)と[遅いクエリを直す](/guides/fix-slow-queries)を参照してください。
