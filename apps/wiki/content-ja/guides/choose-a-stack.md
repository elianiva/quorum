アプリサーバーがキャパシティでは直らない限界にぶつかったとき、またはチームに機能をより速く出してほしいときにこのガイドを使います。

スタックはランタイムとフレームワークです。どのスタックも絶対的に優れているわけではありません。それぞれがスループット、テールレイテンシ、メモリ、チームの出荷速度を引き換えにします。すべての選択肢とその数値は[ランタイムとフレームワーク](/runtimes)にあります。

## まず問題を名づける

1. アプリサーバーを選び、**リソース**のゲージを読みます。
2. 表から自分の問題を探します。直せるスタックを示します。

| 見えるもの                                           | 助けになるスタック                                                                                                                                       |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **RAM** が **CPU** より先に満杯になる。              | リクエストあたりのメモリが小さいランタイム：[Go net/http](/runtimes/go)、[Tokio](/runtimes/tokio)、[Node.js](/runtimes/node)。                           |
| **ビジーワーカー**が満杯で CPU が低い。              | 待つことがワーカーを占有しないランタイム：[Go net/http](/runtimes/go)、[Node.js](/runtimes/node)、[Kestrel](/runtimes/kestrel)。                         |
| 遅いリクエストが 1 つ、すべての種別の p99 を上げる。 | 単一のイベントループを持たないランタイム：[Go net/http](/runtimes/go)、[BEAM](/runtimes/beam)。または[Node.jsクラスターモード](/runtimes/node_cluster)。 |
| p50 は問題なく、p99 が跳ねる。                       | GC の停止がないランタイム：[Tokio](/runtimes/tokio)、[BEAM](/runtimes/beam)。または Java と Go でコレクターを調整します。                                |
| 小さな設計で CPU が満杯になる。                      | より速いランタイム、またはオーバーヘッドの小さいフレームワーク。[OPcache](/research/opcache)が PHP を 2.5 倍速くします。                                 |
| 機能の出荷が遅すぎる。                               | 速く出荷できるフレームワーク：[Laravel](/frameworks/laravel)、[Rails](/frameworks/rails)、[Django](/frameworks/django)。                                 |

速く出荷できるフレームワークは CPU を使い、Laravel、Rails、Django は[Eager loading](/research/eager-loading)をリサーチするまで[N+1 クエリ](/glossary/n1-query)を送ります。

## 選択肢を比べる

1. アプリサーバーの**ランタイム**セクションを開きます。
2. ランタイムにポインタを合わせます。トレードオフカードが、現在のスタックと比べた 6 つの軸と、それがこの設計に何をするかのプレビューを描きます。
3. **フレームワーク**セクションでも同じことをします。そこには、そのランタイムの言語向けのフレームワークだけが並びます。
4. 灰色の選択肢にはリサーチが必要です。ツールチップが、それを解放するリサーチを示します。

言語の給与と採用にかかる時間も比べます。エンジニアはサービスの言語のために採用するので、珍しい言語はチームを高くし、育てるのを遅くします。新しい言語を知らないエンジニアは、訓練するまで遅く働きます。訓練は、解雇して採用し直すより安くつきます。[チームと開発速度](/explanation/team-and-velocity)を参照してください。

## マイグレーションを始める

会社では、スタックの切り替えがサービス全体のマイグレーションを始めます。

1. どのアプリサーバーでも、新しいランタイムかフレームワークを選びます。あるセクションで初めて選ぶときは、トレードオフカードが開いたままです。そのカードの**確定**をクリックします。ゲームがマイグレーションを始め、最初の手順をチームのバックログに置きます。
2. **T** を押してチームパネルを開きます。上部のマイグレーションカードが、古いスタックと新しいスタックを示します。

開発時間のコストは、変更の大きさとコードベースで変わります。同じ言語のランタイムがいちばん安く、フレームワークはそれより高く、新しい言語がいちばん高くつきます。とくに、出荷の遅い言語は高くつきます。

## トラフィックを段階的に移す

マイグレーションは、アプリサーバーを 4 つの段階で新しいスタックへ移します。5%、25%、50%、100% です。これが[ストラングラーパターン](/glossary/strangler-pattern)です。

1. カードが**準備完了**と表示されるまで待ちます。チームがその段階を構築しました。
2. **…% へ切り替え**をクリックします。ゲームがその割合のアプリサーバーを新しいスタックへ移します。それらはコールドで再起動します。**オートパイロット**がオンのときは、ゲームが準備できた各段階を代わりに切り替えます。
3. カードの**バグ**のバッジを見ます。**マイグレーションの不具合修正**のタスクが出荷されるまで、新しいスタックのリクエストは少しの割合で失敗します。そのタスクはゲームがキューに入れます。
4. 各段階のあとに、HUD の Apdex とエラーの割合を確認します。

新しいスタックで状況が悪くなるなら、カードの**キャンセル**をクリックします。移したアプリサーバーは元に戻り、使った開発時間は失われます。最後の段階のあとはキャンセルできません。代わりに不具合を直します。

:::Note{tone="warn"}
マイグレーションが動いているあいだ、機能は半分の速度で構築されます。設計が安定しているときに始め、インシデントの最中には始めません。
:::

## 小さな変更

いつも新しい言語が必要なわけではありません。

- **プールサイズ。** PHP-FPM と Gunicorn では、**プールサイズ**セクションがワーカー数を決めます。数は**RAM に収まる**ワーカー数を超えないようにします。
- **コレクター。** Java では[ZGC](/research/zgc)をリサーチし、**コレクター**で選びます。
- **GOGC。** Go では[Go GCチューニング](/research/gogc-tuning)をリサーチし、**GOGC** を変えます。
- **Node.jsクラスターモード。** [Node.jsクラスターモード](/research/node-cluster)をリサーチすると、すべてのコアを使えます。

ワーカーは独自のスタックで動きます。ワーカーでの変更は、そのワーカーにすぐ効きます。最後の切り替えのあと、マイグレーションカードはマイグレーションの不具合修正が出荷されるまで**移行済み**と表示し、そのあと閉じます。始めたときに満杯だったゲージには余裕ができ、ユーザーのノードの**開発速度**が新しいスタックの出荷の速さを示します。

[イベントループ停止](/sandboxes/event-loop-stall)と[GCポーズ](/sandboxes/gc-pauses)のサンドボックスは、それぞれ 1 つのランタイムの弱さを示します。サンドボックスでは、スタックの変更はマイグレーションなしですぐに効きます。[ランタイムとフレームワーク](/runtimes)がすべての選択肢と数値を並べ、[p99 を読む](/guides/read-p99)が、たったいま後ろにしたかもしれない GC の停止とイベントループの詰まりを扱います。
