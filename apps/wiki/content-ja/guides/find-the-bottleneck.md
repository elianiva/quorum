Apdex が目標を下回り、ユーザーが離れ、どのノードを直せばよいかわからないときにこのガイドを使います。これまでに限界を直したことがないなら、[最初のボトルネック](/tutorials/first-bottleneck)が同じループを手順ごとに教えます。

設計の速さは、いちばん遅いノードで決まります。そのノードが[ボトルネック](/explanation/queues)であり、ほかのどこにキャパシティを足しても資金を使うだけで何も変わりません。

## ノードを見つける

1. 琥珀色の枠が脈打つノードを探します。枠は同時に 1 つのノードだけに付きます。
2. そのノードを選択します。インスペクタが開きます。
3. **負荷**の行を読みます。そのノードの[使用率](/glossary/utilization)が「120/s の 85%」のように表示されます。
4. 行の色を次の限界と比べます。
   - 通常：70% 未満。ノードは健全です。
   - 琥珀色：70% 以上。待ち時間が急速に伸びます。
   - 赤：90% 以上。テールレイテンシが中央値の数倍になります。

ゲームは 1 秒に 1 回、いちばん忙しいノードをそれぞれキャパシティ 2 倍にして試し、いちばん売上を増やすノードに印を付けます。負荷が 60% を超えるノードだけが印を得られます。

どのノードにも枠が付かないなら、キャパシティは売上の制限になっていません。下の「印がないとき」に進みます。

## 埋まっているリソースを見つける

1. インスペクタで、ボトルネックのノードの**リソース**セクションを読みます。
2. いちばん満杯に近いゲージを探します。直し方は表から選びます。

| 埋まったゲージ               | 意味                                                                         | 直し方                                                                                                                             |
| ---------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| CPU                          | ノードがリクエストあたりの仕事をしすぎています。                             | **大きくする**を選ぶか、[ロードバランサー](/components/lb)の背後に 2 つ目のコピーを置きます。                                      |
| ビジーワーカー（CPU は低い） | 下流の遅いノードを待つ間、各リクエストがワーカーを占有しています。           | リクエストを待たせているノードを直します。**RAM に収まる**ワーカー数なら、**ワーカーを増やす**を選びます。                         |
| RAM                          | プロセスがメモリの限界に近づいています。                                     | **ワーカーを減らす**を選ぶか、**大きくする**を選ぶか、**メモリ**ファミリーを選びます。                                             |
| CPUクレジット                | バースト可能なボックスがクレジットを使い切り、CPU のごく一部で動いています。 | **汎用**または**コンピューティング**ファミリーを選びます。                                                                         |
| 接続                         | データベースが接続数の限界に達しています。                                   | [コネクションプーラー](/components/pooler)を置きます。[データベースをスケールする](/guides/scale-the-database)を参照してください。 |

CPU が低いのに「ビジーワーカー」が満杯なのが、いちばんよくある罠です。アプリサーバーは満杯に見えますが、遅いのは背後のデータベースです。これが[リトルの法則](/glossary/littles-law)です。長く待つリクエストほど、ワーカーを長く占有します。

## なぜ忙しいのかを知る

満杯のゲージは、どのリソースが尽きたかを示すだけで、理由は示しません。負荷が上がる理由は 3 つです。リクエストが増える、各リクエストのコストが上がる、ノードのキャパシティが減る、のいずれかです。理由ごとに直し方が違うので、何かを買う前に理由を見つけます。インスペクタの**トラフィックと負荷**セクションには問いごとのブロックがあり、各ブロックの**なぜ？**リンクがこのページの該当箇所を開きます。

### 負荷の変化を読む

**負荷の変化**は、ノードの現在と 1 カレンダー時間前を比べます。

- **トラフィック増加**は需要が伸びたということです。直し方はキャパシティです。サイズを上げる、[ロードバランサー](/components/lb)の背後に 2 つ目のコピーを置く、前に[キャッシュ](/components/cache)を置いて届くリクエストを減らす、のいずれかです。
- **1 リクエストのコスト増加**は、同じリクエストが重くなったということです。キャパシティを増やしても、トラフィックがまた伸びるまで隠れるだけなので、**1 リクエストのコスト**のブロックを読んで何が変わったかを見つけます。
- **キャパシティ減少**は、ノードの余裕が減ったということです。コピーが落ちた、バースト可能なボックスがクレジットを使い切った、再起動でノードが冷えたまま、のいずれかです。

[メトリクス](/research/metrics)があれば、ブロックは変化を需要、1 リクエストのコスト、キャパシティのポイントに分け、合計が変化になります。グラフの破線は、1 リクエストのコストが跳ねた瞬間を示します。そのポイントを選ぶと、跳ねた直後のサンプルを読めます。

### 増幅を読む

[分散トレーシング](/research/tracing)があれば、**増幅**はノードのトラフィックの背後にあるユーザーのリクエスト種別を「300/s × 4.0 = 1,200/s」のように並べます。ユーザーの `checkout` 1 件が、ここでは 4 回の呼び出しになります。

- **1 未満の倍率**は、それらのリクエストの大半がこのノードに届いていないことを意味します。キャッシュが答えた、経路がこのノードを呼んでいない、手前のノードが破棄した、のいずれかです。
- **大きな倍率**が 1 つの種別に出るなら、原因はノードではなくコードです。行ごとに 1 クエリを送る ORM は[N+1 クエリ](/glossary/n1-query)で、[Eager loading](/research/eager-loading)がそれを 1 つにまとめます。
- **リトライとヘッジ**は、トラフィックのうち 2 回目の試行である割合です。ノードが呼び出しに失敗しているのにこれが上がるなら[リトライストーム](/incidents/retry-storm)です。ノードへのリンクに**バックオフ**と**ブレーカー**を設定します。[リトライストームを止める](/guides/stop-a-retry-storm)が手順を追っています。
- **キャッシュミス**は、答えを持っていないキャッシュや CDN を通ってきた割合です。再起動後に高いならキャッシュが冷えています。高いままなら、キャッシュが小さすぎるか TTL が短すぎます。

**最も遅い呼び出し**は、このノードが呼ぶ先でいちばん時間がかかるノードを示します。**ビジーワーカー**が満杯のアプリサーバーでは、まずそのノードを直します。

### コストの内訳を読む

[継続的プロファイリング](/research/profiling)があれば、**受信オペレーション**の各操作が、トラフィックの割合の隣に作業の割合を表示します。限界のリソースをどれだけ使うかです。まれな操作がその大半を使うこともあります。**1 リクエストのコスト**は操作を高い順に並べます。1 つ開くとコストの内訳を読めます。基本コストと、それを掛けるすべての要因です。1 を超える要因は琥珀色で、1 未満の要因はすでに手に入れた改善です。

| 行                                     | どこから来るか                                                   | 何が取り除くか                                                                                                                                                |
| -------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| テーブル肥大                           | VACUUM がまだ掃除していない死んだ行。                            | [テーブル肥大](/incidents/table-bloat)が過ぎます。[保持ポリシー](/research/retention)の期間か MySQL エンジンが防ぎます。                                      |
| ホットシャード                         | 1 つの大きなテナントのキーが 1 つのシャードに載っています。      | [大口テナントのホットシャード](/incidents/hot-shard)：よりよいキーでの[シャーディング](/research/sharding)、または[キャッシュ](/research/caching)。           |
| インデックスのないスキャン             | テーブル全体を読むクエリ。                                       | [スロークエリ](/incidents/slow-query)：[クエリ分析](/research/query-analysis)が欠けたインデックスを見つけます。                                               |
| バッファキャッシュへのレポートスキャン | レポートがホットなページを RAM から追い出します。                | レポートを[データウェアハウス](/components/warehouse)へ移します。[レポートがデータベースを殺す](/incidents/report-db)を参照してください。                     |
| ディスク上のワーキングセット           | データが RAM に収まらなくなっています。                          | サイズを上げるか**メモリ**ファミリー、または読み取り用の[リードレプリカ](/components/replica)。                                                               |
| 機能                                   | クエリを重くする、出荷済みの機能。                               | その機能のコストです。[非正規化](/research/denormalization)が読み取りを安くします。                                                                           |
| インデックス                           | チームが追加した各インデックスが、すべての書き込みを遅くします。 | 速い読み取りの代価です。必要とするクエリにだけインデックスを追加します。                                                                                      |
| シャードファンアウト                   | 検索やレポートがすべてのシャードに問い合わせます。               | 検索には[検索](/components/search)ノード、レポートにはデータウェアハウス。                                                                                    |
| コールドスタート                       | 再起動、または温まっていない JIT ランタイム。                    | 待つか、[高負荷下のJVMウォームアップ](/incidents/jvm-warmup)を参照してください。                                                                              |
| ガベージコレクション                   | ヒープがほぼ満杯です。                                           | RAM を増やすか、よりよいコレクター([ZGC](/research/zgc)、[Go GCチューニング](/research/gogc-tuning))。[GCポーズ連発](/incidents/gc-storm)を参照してください。 |
| スワップ                               | プロセスが RAM を使い切っています。                              | **ワーカーを減らす**、サイズを上げる、または**メモリ**ファミリー。                                                                                            |
| ランタイム、フレームワーク             | スタックの速度と、リクエストあたりのオーバーヘッド。             | [スタックを選ぶ](/guides/choose-a-stack)。                                                                                                                    |
| シリアライズ                           | コードが行う各呼び出しは、出ていくときにエンコードされます。     | 呼び出しを減らすか、[バイナリRPC](/research/binary-rpc)。                                                                                                     |
| アナリティクスのサンプリング           | アナリティクスのタップがこのノードをサンプリングします。         | [アナリティクス](/components/analytics)ノードのサンプリングレートを下げます。                                                                                 |
| ノイジーネイバー                       | 共用テナントのミューテーターがコアをほかへ貸します。             | 何もありません。来ては去ります。                                                                                                                              |

### もしもを試す

[継続的プロファイリング](/research/profiling)があれば、琥珀色か赤のノードを選ぶと**もし**の行が表示されます。今すぐできる 1 つの変更のあとの負荷で、このノード、その前のキャッシュ、呼び出し先でいちばん忙しいノードの**大きくする**や、ノードへのリンクの**リトライなし**などです。各行は実際の設計の短いゴースト実行なので、意外な結果になることもあります。遅いデータベースを待つアプリサーバーを大きくすると、そのデータベースへ通るリクエストが増え、自分自身の負荷が上がります。

行が示すのは何が起きるかであり、何を買うかではありません。選ぶ前に、各行の下がり幅と支出を比べます。

## 直して確認する

1. 変更は 1 つだけにします。
2. ゲーム内で数秒待ち、流れを落ち着かせます。
3. 元のボトルネックの負荷の行が 70% を下回ったことを確認します。
4. HUD の Apdex が目標へ向かって上がったことを確認します。
5. もう一度枠を探します。ふつうは新しいノードへ移るので、最初の手順から繰り返します。

枠が同じノードに残り、負荷が下がらないなら、直したのは間違ったリソースです。ゲージに戻って選び直します。

:::Note{tone="warn"}
**大きくする**とファミリーの変更は、ノードを短いあいだ再起動します。2 つ目のコピーがない単独のノードは、再起動のあいだトラフィックを落とします。
:::

相乗りボックスのサンドボックスは、データベースとアプリサーバーが 1 つのボックスに載った状態で始まるので、どちらのリソースが先に埋まるかを見つけ、支出の上限の中で直せます。

::Sandbox{id="shared-box"}

## 印がないとき

設計は、ボトルネックがまったくないのにユーザーを失うことがあります。次の場所を確認します。

- ノードカードの**赤い「行き場なし」の行**。つながっているどのノードもリクエスト種別を受け付けていません。それを受け付けるノードへリンクを引きます。
- HUD の**エラー**。[構造化ログ](/research/logs)があれば、ユーザーのノードを選んで**原因別エラー**を読みます。
- **離脱の理由。** HUD で**ユーザー**を選びます。各行がリクエスト種別と原因を示します。`slow` の行には、ボトルネックのノードを選んでくれる**表示**ボタンがあります。

## ほかの見つけ方

- **D** を押して[ダッシュボード](/explanation/observability)を開きます。[メトリクス](/research/metrics)を手に入れてからです。**飽和**の行が各ノードの負荷の推移を示します。**高負荷ノード**の数値がいちばん忙しいノードを示します。
- [パーセンタイル](/research/percentiles)があれば、各カードのレイテンシの行が p99 を示します。p99 が高く負荷が低いノードは、キャパシティではなくテールの事象を指します。[p99 とテールレイテンシを読む](/guides/read-p99)を参照してください。
