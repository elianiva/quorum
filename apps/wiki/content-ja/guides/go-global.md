シリーズCの時代に達して海外のユーザーが遅いとき、またはリージョン障害を生き延びる必要があるときにこのガイドを使います。

シリーズCから、ユーザーは 4 つのリージョンに住みます。北米、欧州、アジア太平洋、南米です。各リージョンは自分の Apdex で増えたり減ったりします。Apdex が落ちたときにユーザーがなぜそんなに早く離れるかは[ユーザーと成長](/explanation/users-and-growth)が扱います。どのユーザーも最初は自分のホームリージョンに入るので、遠いユーザーはリクエストごとに海を往復する分を 2 回払います。

## 誰が遅いのかを知る

1. HUD で**ユーザー**を選んで**離脱の理由**を開き、遠いリージョンからの行を探します。
2. **ユーザー**のノードを選んで**リクエスト**を開きます。各種別の平均レイテンシを、シリーズCの前の数値と比べます。
3. [シリーズC](/eras/series-c)のページで、各リージョンがユーザーのどれだけを占めるかを読みます。

キャパシティを増やしても助けになりません。遅れは距離だからです。だからユーザーには、そのユーザーに近いリージョンから提供します。

## 2 つ目のリージョンを開く

1. [マルチリージョン](/research/multi-region)をリサーチします。[マルチゾーン](/research/multi-az)が必要です。
2. ボードの上部のリージョンのタブを探します。閉じているリージョンは **+ EU**、**+ APAC**、**+ SA** と表示されます。
3. 遅いユーザーがいちばん多いリージョンをクリックします。ツールチップが価格を示し、ゲームがそのリージョンを専用のユーザーのノードとともに開きます。
4. 新しいタブをクリックして、そのリージョンのボードを見ます。

## ユーザーを自分のリージョンへ送る

1. [GeoDNS](/research/geo-dns)をリサーチします。これがないと、すべてのユーザーが今もホームのユーザーのノードへ入ります。あると、各リージョンのユーザーが自分のリージョンの、または起動している中でいちばん近いユーザーのノードへ入ります。
2. 新しいタブで、ロードバランサーとアプリサーバーを置き、そのリージョンのユーザーのノードをそれらへリンクします。
3. ノードを選んで**リージョン**セクションを開くと、別の開いたリージョンへ移せます。移したノードは再起動します。

決済プロバイダ、LLM API、プッシュプロバイダ、認証プロバイダ、CDN、アナリティクス、決済はすべてのリージョンに提供します。コピーしないでください。

## データをどこに置くか決める

海外のアプリサーバーがホームのデータベースを呼ぶと、クエリごとにリージョンをまたぐ往復を払います。だからデータのノードごとに 1 つのパターンを選びます。

| パターン                 | 方法                                                                                                              | トレードオフ                                                       |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 現地で読み、ホームへ書く | 新しいリージョンに[リードレプリカ](/components/replica)を置きます。書き込みはホームのデータベースへリンクします。 | 読み取りは速い。書き込みは海を渡る。一部の読み取りは古いまま返る。 |
| リーダーレスストア       | [ワイドカラムストア](/components/wide)で**リージョン**を**分散**に設定します。                                    | 現地のクォーラム。リージョン間は結果整合。                         |
| 合意形成ストア           | [分散SQL](/components/dsql)で**リージョン**を**分散**に設定します。                                               | どこでも正しい。書き込みは遅い。支出はずっと多い。                 |

分散したストアは最大 3 つのリージョンでノードを動かし、それぞれに課金するので、チェックアウトには分散SQL、フィードには[リーダーレスストア](/glossary/leaderless-replication)を使います。[データ層](/explanation/the-data-tier)を参照してください。

[書き込みの取りこぼし](/sandboxes/missed-write)のサンドボックスは、すべての API 読み取りが最新の書き込みを見ることを求めます。

## ミラーで設計をコピーする

各リージョンを手で作るのは遅く、ずれていきます。だから[Infrastructure as Code](/research/infra-as-code)があれば、1 つのリージョンを別のリージョンへミラーします。

1. リージョンのタブの隣の**ミラー**をクリックします。
2. IaCツールを選びます。そのあと「…のミラー先」で、対象のリージョンを選びます。各ボタンが価格を示します。
3. データのノードごとに、ミラーがそれをどうコピーするかを選びます。**リードレプリカ**、**自前のプライマリ**、**リプリケート**、**ソースを呼ぶ**のいずれかです。
4. **適用**をクリックします。新しいノードは適用時間のあとで提供を始めます。
5. あとで、タブの点が、そのリージョンがミラー元からずれたことを示します。もう一度適用するか、変更を例外として保持します。

[GitOps](/research/gitops)はミラーを自分で同期します。一括か**段階的**かです。

## リージョン障害を生き延びる

[リージョン障害](/incidents/region)は、1 つのリージョンのすべてのノードを落とします。グローバルなコンポーネントと、十分な数のリージョンに分散したストアは除きます。

1. アプリサーバーを少なくとも 2 つのリージョンに置き、GeoDNS をオンにします。
2. もう一方のリージョンが必要とするデータをそこに用意します。分散したストアか、そこから提供できるレプリカです。
3. 各リージョンに余裕を保ちます。落ちたリージョンのユーザーは、いちばん近い稼働中のリージョンへ移ります。

この選択が[RPO と RTO](/glossary/rpo-and-rto)を決めます。どれだけのデータを失ってよいか、提供を再開するまでどれだけかかるかです。IPO の前に、DR訓練が自分のホームリージョンをわざと落とします。その手順は[エグジットに備える](/guides/prepare-for-an-exit)が扱います。

## ユーザーのホップを削る

- [エニーキャスト](/research/anycast)は、どこでもユーザーのホップを 20 ms 削ります。
- [HTTP/3](/research/http3)は、遠いユーザーへのホップを 20% 削ります。
- リージョン間の呼び出しにも[エグレス](/glossary/egress)がかかります。各リージョンのアプリサーバーは、できるだけ自分のリージョンのデータを呼ぶようにします。

もう一度**離脱の理由**を開きます。遠いリージョンの行が縮み、HUD の Apdex が目標に戻らなければなりません。

[遠隔ユーザー](/sandboxes/far-away)のサンドボックスは、ユーザーの半分を北米の外に置きます。API の読み取りを平均でその上限の下にします。
