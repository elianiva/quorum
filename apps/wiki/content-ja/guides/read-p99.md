Apdex が目標を下回っているのに平均レイテンシは問題なく見えるとき、または HUD の p99 が平均よりずっと高いときにこのガイドを使います。

p99 は、100 件のリクエストのうち 99 件が下回る時間です。いちばん遅い 1% はその上にあります。平均はその 1% を隠しますが、ユーザーはそれを感じ、その分だけ払いません。理由は[レイテンシとパーセンタイル](/explanation/latency)にあります。

## 始める前に

[パーセンタイル](/research/percentiles)のリサーチが必要です。プレシードで開き、先に[メトリクス](/research/metrics)が要ります。これがないと、ゲームは平均しか表示しません。

## p99 を読む

1. HUD のレイテンシの数値を見ます。パーセンタイルがあれば **p99** と表示され、平均は **μ** のあとに並びます。
2. 2 つの値を比べます。
   - p99 が平均の数倍なら、忙しい設計としてはテールは正常です。
   - p99 が平均の 10 倍以上なら、ごく一部のリクエストが非常に遅くなっています。手順 3 に進みます。
3. **ユーザー**のノードを選択します。インスペクタが開きます。
4. **リクエスト**セクションで、各リクエスト種別の下の行を読みます。その種別の平均、p50、p95、p99 が表示されます。
5. 数値が琥珀色の種別を探します。琥珀色は、その p99 が Apdex の目標を上回っているという意味です。赤い数値は、その種別がよく失敗もしているという意味です。

種別ごとに目標は別です。API の読み取りは速くなければなりません。レポートは数秒かかってもかまいません。[各時代のリクエスト構成](/eras)が、扱う種別を並べています。

## テールを作っているノードを見つける

1. 各ノードカードの**レイテンシ**の行を読みます。パーセンタイルがあれば、平均のあとに p99 が表示されます。
2. 遅い種別の経路を、ユーザーのノードからデータ層までたどります。
3. p99 が平均よりずっと跳ねる最初のノードを見つけます。

## パターンと原因を合わせる

表でパターンを見つけ、原因を名づけ、その直し方を適用します。

| 見えるもの                                                                  | 原因                                                                                                         | 直し方                                                                                                                                                                                |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ノードの負荷が琥珀色か赤で、その上のどの種別も遅い。                        | いっぱいに近いキャパシティでの待ち行列。                                                                     | キャパシティを足します。[ボトルネックを見つける](/guides/find-the-bottleneck)を参照してください。                                                                                     |
| Node.js のアプリサーバーで、どの種別の p99 も高く、ログインがその上にある。 | CPU の重いリクエストが 1 つ、[イベントループ](/glossary/event-loop)を塞いでいます。                          | [libuvスレッドプール](/research/libuv-pool)をリサーチするか、[認証プロバイダ](/components/auth)を置くか、[Node.jsクラスターモード](/research/node-cluster)を使います。                |
| Java か Go のアプリサーバーで、p50 は普通で p99 が高い。                    | [ガベージコレクションの停止](/glossary/gc-pause)。                                                           | RAM を増やすために**大きくする**を選びます。Java なら**コレクター**で ZGC を選びます([ZGC](/research/zgc))。Go なら **GOGC** を変えます([Go GCチューニング](/research/gogc-tuning))。 |
| 新しい Java のコピーが起動した直後に p99 が上がる。                         | [JITウォームアップ](/glossary/jit-warmup)：新しいコピーは最初は遅く動きます。                                | [オートスケーラー](/components/autoscaler)の最小値を上げて、コピーを温かいまま保ちます。                                                                                              |
| 多くのリクエストが呼ぶ 1 つのノードだけで p99 が高い。                      | [大規模環境のテール](/glossary/tail-at-scale)：遅いバックエンドが 1 つあると、リクエスト全体が遅くなります。 | まずそのバックエンドを直します。                                                                                                                                                      |

そのあとゲーム内で少し待ち、2 つを確認します。ユーザーのノードの下の琥珀色の数値が通常に戻ること、HUD の Apdex が上がることです。p99 が変わらないなら、原因は経路の別のノードにあります。ユーザーのノードからまたたどり直します。

:::Note{tone="tip"}
種別の p99 は、その種別の目標を超えたときにいちばん問題になります。目標より遅いリクエストは半分しか稼ぎません。目標の 4 倍遅いリクエストは何も稼ぎません。
:::

## テールを時間で見る

- **D** を押してダッシュボードを開きます。**レイテンシ**のグラフが、平均と p50、p95、p99 の線を描きます。p99 がほかの線から離れた瞬間を探します。
- HUD で**ユーザー**を選び、**離脱の理由**を開きます。`slow` の行が、種別の p99 と目標を並べ、その種別が Apdex のどれだけを奪っているかを示します。
- [アラート](/research/alerting)をリサーチすると、p99 が高いままのときに呼び出しを受けられます。

[イベントループ停止](/sandboxes/event-loop-stall)のサンドボックスは、Node.js をログインと同じアプリサーバーで動かします。パスワードのハッシュが遅くなっても、p99 をその上限の下に保ちます。ガベージコレクションは[GCポーズ](/sandboxes/gc-pauses)のサンドボックスで試せます。

::Sandbox{id="event-loop-stall"}

用語集が[パーセンタイル](/glossary/percentile-p50-p95-p99)を定義し、[Apdex と売上](/explanation/apdex-and-revenue)が遅いリクエストがどう金を失うかを説明し、[インサイトと可観測性](/explanation/observability)が各リサーチで何が見えるようになるかを説明します。
