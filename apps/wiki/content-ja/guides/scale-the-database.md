データベースが[ボトルネック](/guides/find-the-bottleneck)のとき、またはインスペクタで赤か琥珀色の注記が出ているときにこのガイドを使います。

アプリサーバーは簡単にコピーできます。データベースはできません。状態を持っているからです。だから 2 つの方法でスケールします。大きなボックスを与えるか、仕事を減らして送るかです。理由は[データ層](/explanation/the-data-tier)にあります。

## 限界を見つける

1. データベースを選択します。インスペクタが開きます。
2. パネルの上部の注記を読みます。それぞれが違う限界を示します。
   - 「クエリ…/s を拒否中：接続が多すぎます。」接続の上限がいっぱいです。
   - 「ワーキングセットが RAM に収まりません：読み取りがディスクに当たります。」ホットなデータがメモリより大きいので、読み取りが遅いです。
   - 「CPUクレジットが尽きました：CPU は 20% に制限されています。」バースト可能なボックスがクレジットを使い切りました。
   - 「新しいクエリにインデックスがありません。」スロークエリのインシデントが動いています。[スロークエリを直す](/guides/fix-slow-queries)に進みます。
3. **リソース**を開き、いちばん満杯のゲージを探します。**CPU**、**RAM**、**接続**のどれかです。
4. **ユーザー**のノードを選んで**リクエスト**を開き、どのリクエスト種別を扱っているかを控えます。種別ごとに違うクエリをデータベースへ送るからです。

限界に合う下のセクションを使ってください。

## 接続がいっぱい

Postgres は接続ごとに 1 つのプロセスを開き、100 まで使えます。アプリサーバーのコピーはそれぞれ自分の接続を持つので、アプリサーバーを増やすとデータベースを落としかねません。

1. [コネクションプーリング](/research/pooling)をリサーチします。
2. アプリサーバーとデータベースの間に[コネクションプーラー](/components/pooler)を置きます。各アプリサーバーをプーラーへ、プーラーをデータベースへリンクします。
3. **プーリングモード**は**トランザクション**のままにします。このモードでは、多くのアプリの接続がデータベースへの 20 本の接続を共有します。**セッション**モードはクライアントごとに 1 本必要で、ほとんど助けになりません。
4. 変更後にリクエストが `crash` で失敗するなら、チームパネル (T) で**セッション状態の廃止**のタスクをキューに入れます。トランザクションプーリングは、セッション状態を保つコードを、そのタスクが出荷されるまで壊すからです。

接続のゲージが下がり、「拒否」の注記が消えることを確認します。

[接続上限](/sandboxes/connection-limit)のサンドボックスでは、デプロイがすべてのプールを 2 倍にします。

## CPU がいっぱい

1. **インスタンス**セクションで**大きくする**を選びます。サイズを 1 段上げるごとに vCPU と RAM が 2 倍になります。
2. それでもデータベースがボトルネックなら、読み取りを外します。
   - [キャッシュ](/research/caching)をリサーチし、アプリサーバーとデータベースの間に[キャッシュ](/components/cache)を置きます。ホットなデータが収まるあいだ、読み取りにメモリから答えます。書き込みは通過します。
   - [リードレプリカ](/research/replication)をリサーチし、[リードレプリカ](/components/replica)を置きます。データベースをそこへリンクしてデータグループに加え、アプリサーバーをそこへリンクします。読み取りのクエリにだけ答えます。
3. Laravel、Rails、Django を使っているなら、[Eager loading](/research/eager-loading)をリサーチしてそのタスクをキューに入れます。これらの ORM フレームワークは、1 つで済む読み取りクエリを何本も送るからです。[N+1 クエリ](/glossary/n1-query)を参照してください。

データベースの負荷の行が 70% を下回り、枠が離れることを確認します。

:::Note{tone="warn"}
**TTL** の長いキャッシュはヒットが増え、古いデータをより多く配ります。リードレプリカは書き込みより遅れるので、一部の API 読み取りは `stale` で返ります。[read-your-writesルーティング](/research/ryw-routing)をリサーチし、各アプリサーバーの**過負荷**セクションで**自分の書き込みを読む**を設定して、書き込みのあとの読み取りをプライマリへ送ります。
:::

[読み取り中心](/sandboxes/read-mostly)のサンドボックスでは読み取りが支配的で、支出の上限の下で作業します。[スタンピード](/sandboxes/stampede)のサンドボックスでは、キャッシュが空の状態で再起動します。

## 読み取りがディスクに当たる

1. **インスタンス**セクションを開き、**メモリ**ファミリーを選びます。vCPU あたりの RAM が汎用の 2 倍あります。
2. または**大きくする**を選んで RAM を増やします。
3. 「読み取りがディスクに当たる」の注記が消えることを確認します。

ワーキングセットはユーザーとともに育つので、この注記は成長とともに戻ってきます。

各変更のあと、ゲーム内で数秒待ち、データベースの負荷の行が通常で 70% 未満であること、HUD の Apdex が目標へ向かって上がることを確認します。[構造化ログ](/research/logs)があれば、ユーザーのノードを選んで**原因別エラー**を読み、`refused`、`stale`、`crash` がほぼゼロに留まるようにします。

## 仕事を正しいストアへ移す

データベースはほぼどのクエリにも答えられますが、量が増えると苦手です。時代が進んで新しいリクエスト種別が来たら、そのクエリに専用のコンポーネントを与えます。

| 仕事の種類                 | コンポーネント                                              | リサーチ                                           |
| -------------------------- | ----------------------------------------------------------- | -------------------------------------------------- |
| 検索クエリ                 | [検索エンジン](/components/search)                          | [全文検索](/research/full-text-search)             |
| アップロードされたファイル | [オブジェクトストレージ](/components/storage)               | [オブジェクトストレージ](/research/object-storage) |
| 遅い仕事、エクスポート     | [キュー](/components/queue)と[ワーカー](/components/worker) | [メッセージキュー](/research/queues)               |
| レポート                   | [データウェアハウス](/components/warehouse)                 | [データウェアハウス](/research/data-warehouse)     |

プライマリでのレポートはバッファキャッシュも追い出すので、ほかのすべての種別が遅くなります。データウェアハウスは[レポートがデータベースを殺す](/incidents/report-db)のインシデントを止めます。

[プライマリでの分析](/sandboxes/analytics-primary)のサンドボックスでは、レポートがすべてのテーブルをスキャンします。

## データベース 1 つで足りないとき

2 つ目のデータベースはフォロワーではありません。1 つのデータセットを持つデータベースをまとめて囲むと**データグループ**になり、そのトポロジーを選びます。

1. 2 つ目のデータベースを置きます。
2. 両方のデータベースを Shift を押しながら選び、**ノードを囲む**を押します。単一プライマリのデータベースを 2 つ以上まとめた箱は、シャードになります。1 つの箱が 1 つのデータセットを持つからです。
3. どちらかのデータベースを開き、**トポロジー**で**シャード**か**マルチリーダー**を選びます。

データベースが 1 つだけのグループには行をコピーする先がないので、選択はすぐに反映されます。グループでデータベースが 2 つ動き始めると、さらなる切り替えには再シャーディングのように 24 開発時間とグループの行のコピーがかかります。

- **シャード**は行をデータベース間に分けるので、書き込みがスケールします。トランザクションはできるだけ 1 つのシャード内に収めます。シャードをまたぐトランザクションは最大 3 倍のコストがかかり、どちらのシャードでも失敗しえます。
- **マルチリーダー**はすべての行をすべてのデータベースへコピーするので、どれでも書き込みを受け付けます。certification が競合する書き込みを落とし（先にコミットしたものが勝ち）、各書き込みは CPU の 1.25 倍を使います。

各グループは行の一部をサービス単位で分けて持つので、2 つ目のグループは、1 つのボードで 2 つの独立したプロダクトを動かす方法です。データベースの入っていない箱は領域を描くだけです。

シリーズCの時代から、リーダーレスと合意形成のストアは複数のノードで書き込みを受け付けます。

- [ワイドカラムストア](/components/wide)は各キーを N 個のノードへ複製し、クォーラムを調整できます。[リーダーレスレプリケーション](/research/leaderless)をリサーチします。
- [分散SQL](/components/dsql)はトランザクションをレプリカの過半数に保ちます。[合意形成データベース](/research/consensus)をリサーチします。

どちらもデータベースよりずっと多くの支出がかかります。キャッシュとレプリカを付けた最大のデータベースでも追いつけないとき、またはリージョン障害を生き延びる必要があるときだけ移ります。[グローバルに展開する](/guides/go-global)を参照してください。
