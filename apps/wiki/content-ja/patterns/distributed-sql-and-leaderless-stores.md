複製と分割はストアに任せます。速さならリーダーレス、正しさなら分散 SQL です。

## ステップを進める時期

- 手作業のリシャーディングに割く開発時間がなく、シャードをまたぐトランザクションが失敗しています。
- フィードやログのワークロードが、単一のプライマリが受けられる量をはるかに超えて書き込みます。
- チェックアウトがあらゆる場所で正しくなければならず、遅れるレプリカは受け入れられません。

## 設計

::Design{id="quorum-store"}

リーダーレスのワイドカラムストアは各キーを N 個のノードへ複製します。読み取りはそのうち R 個に問い合わせ、書き込みは W 個を待ちます。ストアが扱わない種別のためにデータベースがそばに残ります。

::Design{id="distributed-sql"}

分散 SQL は SQL のストアを Raft に載せます。各書き込みはレプリカの多数派を待つので、すべての読み取りがそれを目にします。

## なぜうまくいくのか

R と W の合計が N を超えると、読み取りは必ず最新の書き込みを受けたノードに当たります。R や W を下げると速くなり、古い読み取りが通ります。分散 SQL はその保証をトランザクションに対して与え、書き込みごとのレイテンシが増えます。

強いクォーラムでもトランザクションではありません。ワイドカラムストアでのチェックアウトはやはりときどき壊れるので、お金には分散 SQL、フィードにはリーダーレスストアを使います。

## コスト

どちらも一度に複数のノードの費用がかかり、分散 SQL が最も高くつきます。どちらも検索やアップロードは扱わないので、データベースがそれらのために残ります。分断はレプリカを失うことがあり、すべてのレプリカを必要とするクォーラムはそのとき拒否します。どちらも**スプレッド**でリージョンにまたがれ、マルチリージョンのステップがそれを使います。ゲームはワイドカラムストアの軽量トランザクションをモデル化していません。
