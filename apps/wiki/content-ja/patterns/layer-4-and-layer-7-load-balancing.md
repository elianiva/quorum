レイヤー 4 のバランサーは中身を見ずに接続を転送し、レイヤー 7 のバランサーはリクエストを読んで、見つけた内容で決めます。

## 使うとき

- L7: 失敗した呼び出しを別のサーバーで再試行したい、あるいは対象の健全性を HTTP で確認したいとき。
- L4: 生のスループットと低いレイテンシが振り分けより重要、あるいはトラフィックが HTTP でないとき。
- どちらでも: 1 台のバランサーがボード上で最も忙しいノードになっているとき。

## 仕組み

L4 バランサーは IP アドレスとポートで動きます。バックエンドを 1 つ選んでバイトを流すので、リクエストあたりの仕事が少なく、非常に大きな量を扱えます。L7 バランサーは接続を終端し、HTTP を解析し、`/api` を 1 つのプールへ、`/images` を別のプールへ送れ、ヘッダーを足し、再試行できます。実例は AWS の Network Load Balancer が L4、Application Load Balancer が L7 です。

プールを種類別に分けると、互いを隔離できます。ページビューの洪水が API サーバーを飢えさせられません。Quorum はその分割を [APIゲートウェイ](/components/gw) に任せ、バランサーは届いたものを散らすだけにします。

## コスト

L7 はリクエストあたりの仕事が多く、上限が低く、リクエストあたりのコストが高く、レイテンシも加えます。L4 はパスが見えずリクエストを再試行できず、接続単位で負荷を散らすので、1 つの長命な接続が 1 台のサーバーを占有しえます。

## Quorum では

[ロードバランサー](/components/lb) には種類があります。L7 が既定で、L4 には [L4ロードバランシング](/research/l4-lb) が必要です。L4 はすべてのリンクのすべての種類のリクエストを転送します。どちらの種類も種別で振り分けません。`page` をあるサーバー群へ、`read` を別の群へ置くのは [APIゲートウェイ](/components/gw) の仕事です。
