# Rust kernel research

An experiment: rewrite the `@quorum/simulation` solver in Rust, compile it to
`wasm32-unknown-unknown`, and measure it against the TypeScript package. This is research
code. No production code imports it.

The goal is bit-identical results to TypeScript on the same inputs. Every layer is checked
against a TypeScript harness that runs the same board through both implementations and
compares figures. `NOTES.md` records the Rust patterns the port adopted and why.

## Build

```sh
rustup target add wasm32-unknown-unknown   # once
cargo build --release --target wasm32-unknown-unknown
```

The wasm lands at `target/wasm32-unknown-unknown/release/qsim.wasm`. The harnesses load it
from there. There is no `unsafe` in the crate and no dependency: `Cargo.toml` has none.

## Harnesses

Run with `node <file>.ts` (Node 26 strips types). Each prints a match count and, where
relevant, a timing comparison.

- `gen-catalog.ts` writes `src/catalog.rs` from the TypeScript catalog. Re-run it after any
  catalog change.
- `harness.ts` is the one place that fills the kernel's blocks from a Game and reads the
  figures back; every other harness imports it, so the ABI has one owner.
- `fuzz-dist.ts` compares the outcome algebra on 3,000 random inputs.
- `splits.ts` compares routing splits on even and uneven weights.
- `forward.ts` compares arriving rates and model figures for the stress board, with timings.
- `outcomes-check.ts` compares the outcome tree figure by figure, failures included.
- `bench.ts` compares and times `solveFlow`, `solve`, and `bottleneckOf`, and reports the
  memory each side holds.

## Measured on the 200-Node stress board

Apple Silicon, one `node` process, means of 40 samples after warm-up. TypeScript is the
package as shipped; Rust is the raw `cargo` release artifact, without `wasm-opt`.

| Figure                          | TypeScript    | Rust          | Speedup |
| ------------------------------- | ------------- | ------------- | ------- |
| `solveFlow` (6 passes + Ledger) | 8,241 µs      | 790 µs        | 10.4×   |
| `bottleneckOf` (3 candidates)   | 2,522 µs      | 338 µs        | 7.5×    |
| `solve` (flow + search)         | 9,056 µs      | 1,064 µs      | 8.5×    |
| Ledger held                     | 448 KB (JSON) | 23 KB (block) | —       |

The solve converges in 3 passes on this board, in both implementations. Revenue matches to
the last bit: 377.45804081548965 on both sides.

`NOTES.md` explains where the time went: work that reads only the Design or the Game is
done once per Design instead of once per pass, the search reuses the flow solve's Ledger
instead of solving again, and a tree reset moves an epoch instead of zeroing its tables.

## What is ported, and what is not

Ported in full, and compared figure by figure: the catalog, the outcome algebra, the three
capacity models, routing splits, the forward pass, the outcome tree for `users`, `lb`,
`dns`, `cdc`, `pooler`, `database`, `replica`, `server`, `auth`, `msgp`, `warehouse`,
`psp`, `llm`, `storage`, `gpu`, `search`, `wide`, `queue`, `worker`, `cache`, `waf`, `vec`, `dsql`,
`doc`, `cdn`, `edge`, `ws`, `log` and the Components whose rule is a
terminal `stranded`, the revenue and the Ledger figures the solve reads (revenue, demand,
served, Apdex, latency, percentiles, errors, fines, per-kind rows, per-Node rows, per-kind
bottleneck), the pass loop with its convergence test and feedback, and the Bottleneck
search.

`node challenges.ts` solves every Challenge's opening board on both sides. All 32 are
identical in every figure and in the Bottleneck. `node trajectory.ts 1` plays every
Challenge's canonical run and compares the Game after every Step: all 12,752 Steps are
identical, including the ones with an incident running. A scratch sweep also forced each of
the 56 incident kinds on every Challenge board and compared 6 Steps of each.

Not ported yet, and refused rather than approximated: a Game with a shipped Feature or a
Product lever; and any Component whose `outcome` rule is not in the list
above (`gw` and `fn`). A run over such a Design returns status 6 instead of a figure. The
presentation-only halves of the TypeScript Ledger (bills, Insight, velocity, Link rows,
regions, devices, services, market, forecast) are not ported, because no figure the solve
reads depends on them.

## Open problems

- `gw` and `fn` have no rules yet, so a board with one is refused. No Challenge uses
  either.
- `gen-catalog.ts` mirrors two lists it cannot import — `GLOBAL_COMPONENTS` from
  `regions.ts` and the per-Component `fixed` flag is imported but the zone lists are not
  exported — so a change there needs the generator edited by hand.
- The `Feature` tables are not generated, which is why a Game that ships one is refused
  rather than read at full exposure.
